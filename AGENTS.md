# Ferrite

## Цель проекта
Высокопроизводительная независимая реализация сервера (позже, возможно,
клиента) для Minecraft: Java Edition на Rust. Сервер должен:
- работать с официальным клиентом выбранной версии по сетевому протоколу;
- поддерживать большое число игроков за счёт многопоточной архитектуры;
- уметь открывать существующие миры (формат Anvil).

Клиент (позже): отдельная программа на Rust + wgpu, подключается к
серверам. Совместимость с Java-модами не цель.

## Целевая версия
Одна фиксированная версия протокола: **26.3** (protocol version **777**).
Поддержка других версий не делается, пока целевая не стабильна.

## Юридические правила (строго)
- Clean-room: никакого декомпилированного или деобфусцированного кода Mojang.
- Источники: документация протокола сообщества, собственные эксперименты
  с сетевым трафиком, открытые проекты с совместимой лицензией (с учётом лицензии).
- Не включать в репозиторий оригинальные ассеты (текстуры, звуки, модели).
- Не использовать слово «Minecraft» в названии, пакетах и логотипах.
- Перед копированием кода из других проектов проверять лицензию.

## Технологии
- Rust (stable), edition 2021+, workspace из нескольких crates.
- Async-сеть: tokio. Игровая логика: ECS (bevy_ecs или hecs).
- Сериализация: собственный кодек протокола, NBT через отдельный crate.
- Тесты: cargo test, бенчмарки: criterion.

## Архитектура (crates)
- `ferrite-protocol`: пакеты, кодеки, состояния соединения.
- `ferrite-nbt`: чтение/запись NBT.
- `ferrite-world`: чанки, Anvil, генерация мира.
- `ferrite-server`: тик-цикл, сущности, игроки, команды.
- `ferrite-net`: сетевой слой.
Зависимости направлены вниз: server -> world, net -> protocol -> nbt.

## Правила разработки
1. Работать маленькими шагами: одна задача = один коммит/PR.
2. Перед кодом коротко описать план; после кода указать, как проверить.
3. Не писать `unsafe` без комментария с обоснованием.
4. Без `unwrap()`/`expect()` в серверном коде, кроме тестов; ошибки через
   `thiserror`/`anyhow`.
5. Всё в тик-цикле не должно блокироваться: тяжёлые задачи в отдельные потоки.
6. Каждый новый пакет протокола сопровождается тестом на кодирование/декодирование.
7. Перед коммитом: `cargo fmt`, `cargo clippy -- -D warnings`, `cargo test`.
8. Производительность: сначала измерить (criterion, flamegraph), потом оптимизировать.
9. Не добавлять зависимости без необходимости, указывать причину.
10. Если не уверен в поведении игры, не придумывать: пометить `TODO(verify)`
    и спросить.
11. Перед каждым новым пакетом сверять поля и порядок с документацией протокола
    для 26.3 и сохранять пример реального трафика в тестах.

## Порядок работы (дорожная карта)
1. Handshake, Status (пинг сервера в списке).
2. Login (offline-режим), затем online-режим с шифрованием.
3. Отправка чанков, плоский мир.
4. Движение игрока, чат, команды.
5. Чтение/запись Anvil.
6. Генерация мира, блоки, физика.
7. Мобы, инвентарь, редстоун.
8. Оптимизация многопоточности, нагрузочные тесты.

## Формат ответов агента
- Отвечать на русском, код и комментарии в коде на английском.
- Кратко объяснять решения, не переписывать файлы без нужды.

## Честность и проверяемость (строго)

1. Если тест падает, чини код, а не тест. Нельзя менять ожидаемые значения,
   ослаблять assert или удалять тесты без явного объяснения причины
   и моего подтверждения.
2. Запрещено без согласования: `#[ignore]`, `#[allow(...)]`, `todo!()`,
   `unimplemented!()`, `unwrap_or_default()` на ошибках, молчаливый `Ok(())`.
3. Заглушки допустимы только с пометкой `TODO(stub)` в коде и отдельной строкой
   в итоговом отчёте.
4. Запрещено возвращать константы или подгонять логику под конкретный тест.
5. Факты о протоколе (ID пакетов, порядок и типы полей, номера версий) нельзя
   брать из памяти. Каждый факт сопровождается ссылкой на источник
   в комментарии. Нет источника: `TODO(verify)` и вопрос мне.
6. Тесты кодека проверяют только согласованность с самим собой. Для совместимости
   нужны эталонные байты из реального трафика (`tests/fixtures/`) с описанием,
   откуда они получены.
7. В отчёте разделять: что запущено и прошло, что не запускалось,
   что реализовано частично. Фразы вроде "всё работает" без перечня
   выполненных команд не принимаются.
8. В конце каждой задачи показывать вывод `cargo fmt --check`,
   `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`
   и список изменённых тестов (если были), с причиной.
9. Не трогать файлы вне задачи, не менять CI-конфиг и этот файл без запроса.
