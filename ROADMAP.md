# Ferrite: дорожная карта

Последнее обновление: 2026-11-28.
Правила работы агента: `AGENTS.md` (приоритетнее этого файла).
История изменений: `CHANGELOG.md`.

## Цель

Независимая реализация сервера Minecraft: Java Edition на Rust.

- Целевая версия: **26.3, протокол 777** (подтверждено реальным клиентом).
- Работает с официальным клиентом по сетевому протоколу.
- Конечная цель: много игроков в одном мире без деградации тика.
  Измеримая формулировка: «N игроков держат 20 TPS на указанном железе»
  (N и железо фиксируются на этапе 8 по результатам замеров).
- Клиент на Rust: только после того, как сервер стабилен. Не цель на ближайшее время.

## Принципы

1. Сначала работоспособность, потом оптимизация, и только по замерам.
2. Источник истины о протоколе: поведение реального клиента и записи
   трафика, а не схемы из памяти или PR сторонних проектов.
   Схема другой версии (например, 26.1) подсказка, а не факт:
   в 26.3 ID уже сдвинулись.
3. Clean-room: никакого кода и ассетов Mojang в репозитории.
   Данные реестров и тегов хранятся только локально (`server-data/`,
   `recordings/` в `.gitignore`).
4. Один шаг = один коммит, зелёный CI, ревью diff человеком.
5. Каждое исправление безопасности начинается с теста, который падает.
6. Сеть не знает про мир, игровая логика не владеет сокетами.

## Этап 2.3: Configuration

Цель: клиент 26.3 проходит Configuration, получает Finish Configuration
и переходит в Play.

Наблюдённые ID (запись Purpur 26.3, протокол 777; направления относительно
сервера; названия пакетов выведены по порядку и размерам, помечать
`TODO(verify)`):

| Пакет | S2C | C2S |
|---|---|---|
| Custom Payload (бренд) | 0x01 | 0x02 |
| Client Information | | 0x00 |
| Feature Flags | 0x0d | |
| Select Known Packs | 0x0f | 0x07 |
| Registry Data (32 пакета в записи) | 0x07 | |
| Update Tags | 0x0e | |
| Finish Configuration / Acknowledge | 0x03 | 0x03 |

Шаги (каждый: запуск с клиентом, лог, коммит):

1. Custom Payload и Client Information. Свой бренд сервера.
2. Feature Flags и Select Known Packs: структура по записи.
3. Registry Data: минимальный набор. Начать с идентификаторов без
   встроенных данных. Каждое изменение по тексту ошибки клиента.
4. Update Tags: сначала пустой, затем минимально необходимое.
5. Finish Configuration и приём Acknowledge.

Заменить `SessionPhase` на линейный async-поток
(handshake, login, configuration), лимит фрейма до Configuration 4 КиБ
поднять там, где нужно.

Данные реестров: только из локального `server-data/configuration-26.3.json`
(`server-data/` добавлен в `.gitignore` в `903962f`). Источники наполнения:
`--reports` официального `server.jar` или запись трафика. В тестах только
синтетические идентификаторы `ferrite:test_*`. Согласовать способ с
человеком до написания кода шага 3.

Критерий: клиент доходит до Play (подтверждается логом и экраном клиента).

## Этап 3: Play (минимум)

Join Game, позиция игрока, пустой чанк, keep-alive, корректное
отключение. Замер времени тика в логе с первого дня.
Критерий: клиент заходит в пустой мир и остаётся подключённым.

## Этап 4: плоский мир

Формат чанка, отправка чанков вокруг игрока, простая генерация плоского
мира, движение, чат, команды. Загрузка и генерация чанков вне тика.

## Этап 5: несколько игроков

Видимость сущностей через пространственную сетку, рассылка только
соседям, сериализация события один раз для многих получателей.
Простой бот-нагрузчик (N подключений) появляется здесь.

## Этап 6: хранение мира

NBT (`ferrite-nbt`), чтение и запись Anvil, открытие существующих миров.

## Этап 7: механика

Блоки и физика, мобы, инвентарь, редстоун. Самая трудоёмкая часть
ванильной совместимости. Неуверенное поведение помечать `TODO(verify)`.

## Этап 8: производительность

Только по замерам. Кандидаты: ECS, параллельные системы без общих данных,
деление мира на независимые регионы, пулы буферов, нагрузочные тесты
(criterion, flamegraph). Зафиксировать целевой показатель (N игроков,
20 TPS, железо) и измерять против него.

## Этап 9: клиент (опционально)

Rust и wgpu. Не раньше стабильного сервера. Ассеты только из
лицензионной копии пользователя.

## Известные открытые вопросы

- `Intent::Transfer` (3): поведение в 26.3 не проверено (`TODO(verify)`).
- `session_id` в Login Success: у официального сервера случайный UUID v4,
  у нас нулевой UUID (клиент принял для Login). Проверить на этапе Play.
- Запись Configuration снята на Purpur, не на ванильном `server.jar`.
  Повторить на ваниле и сравнить таблицу ID.
- `Login Disconnect` на реальном клиенте не проверен (только тестом).
- Рекордер: возможная гонка `write_all` и `tap.feed`, зависание
  полузакрытого сокета (отложено).
- Серверу без локального `server-data/` Configuration не пройти.
  Позже: генерация из собственной копии игры пользователя.
- `actions/checkout@v4` на Node 20 (предупреждение): обновить отдельным
  мелким коммитом.

на диапазоне изменений `pre-configuration..HEAD` (предыдущие контрольные
теги: `stage-1-done` на `132cd94`, `pre-configuration` перед этапом 2.3).
Результаты проверять воспроизведением: замечание без воспроизведения гипотеза.
